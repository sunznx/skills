# Planning with Files integration

The installed `planning-with-files` (PWF) skill owns plan selection, modes,
and progress updates; follow its instructions. Archify adds an artifact
location convention; its CLI continues to accept explicit input/output paths.

## Prepare the artifact directory

Use the user's project root, keeping the Archify installation separate from
the project being diagrammed. Once PWF has selected the plan, read its
`task_plan.md`, `findings.md`, and `progress.md`, then create
`<PLAN_DIR>/archify/`. Give each diagram a stable, descriptive subdirectory
such as `request-lifecycle/`. Record the plan identity and artifact directory,
then complete discovery below before reading the matching schema and example.
This preserves the fast author's next-tool-action candidate write.

Resolve PWF scripts relative to its installed skill, and Archify scripts
relative to the Archify installation. Use absolute paths from the user's
project. Bind `PLAN_ID` and `PWF_PLAN_ROOT` in each shell invocation when the
tool does not preserve environment variables between calls.

## Discover and reuse

Check the selected plan's recorded paths and `<PLAN_DIR>/archify/`, then paths
explicitly supplied by the user or project documentation. Inspect only relevant
candidates within the authorized scope. Report what is reusable or why a new
diagram is needed; do not search other task plans or installation examples for
project facts.

Reuse compatible JSON after checking its diagram type, subject, scope, and
source freshness. A valid schema or old receipt does not establish current
facts. Copy a source outside the selected artifact directory into it before
editing, leaving the original intact; record the source path and any inspected
revision or digest in `findings.md`. Preserve stable IDs for continuing entities
and meaningful relationship labels. Adapt Mermaid using the existing Mermaid
route. HTML/images alone require semantic reconstruction before authoring JSON;
disclose missing evidence. Ask only when competing sources remain unresolved.

Update the working candidate during repair. Preserve prior completed deliveries
when starting a distinct scope or revision by choosing a new subdirectory. For
repairs to the current output, retain `deliver`'s atomic last-good behavior.

## Artifact bundle and commands

Default bundle, all within the selected diagram subdirectory:

- `<diagram-id>.<type>.json`: editable specification.
- `<diagram-id>.html`: trusted output after successful `deliver`.
- `validation.receipt.json`, `delivery.receipt.json`: captured command output,
  with exit codes recorded in `progress.md`.
- Browser receipts, screenshots, and contact sheets: keep the filenames and
  relative relationships generated by `visual-check`, beside the HTML.
- Requested exports and any supplementary visual-review record.

PWF metadata belongs in planning records, not additional diagram schema fields.
Use explicit absolute CLI output paths instead of relying on `meta.output` or
changing the working directory to the installed skill:

```sh
ARCHIFY_SKILL_DIR="<absolute-archify-installation>"
PLAN_DIR="<absolute-directory-returned-by-pwf-resolver>"
ARTIFACT_DIR="$PLAN_DIR/archify/request-lifecycle"
node "$ARCHIFY_SKILL_DIR/bin/archify.mjs" validate sequence "$ARTIFACT_DIR/request-lifecycle.sequence.json" --quality showcase --json > "$ARTIFACT_DIR/validation.receipt.json"
node "$ARCHIFY_SKILL_DIR/bin/archify.mjs" deliver sequence "$ARTIFACT_DIR/request-lifecycle.sequence.json" "$ARTIFACT_DIR/request-lifecycle.html" --quality showcase --json > "$ARTIFACT_DIR/delivery.receipt.json"
node "$ARCHIFY_SKILL_DIR/bin/archify.mjs" visual-check "$ARTIFACT_DIR/request-lifecycle.html" --json
```

These are separate steps: inspect each command's exit code and receipt before
the next one. Run `visual-check` only after the current candidate's delivery
succeeds. Capture stderr and failures in the selected plan without presenting
old output as the new delivery. The [delivery contract](delivery-contract.md)
remains authoritative for hashes, sidecars, browser and visual-review statuses.

Honor an explicit user output destination while retaining a canonical bundle
under the selected plan. After acceptance, copy the requested standalone HTML
or export to that destination and record both paths. When the user requests the
evidence bundle too, keep sidecars together and preserve their relative links.
Keep original receipts unchanged and verify copied bytes; copies do not gain
new validation or browser-review claims.

## Record and hand off

The plan owner updates phases using PWF. Put source findings, coverage gaps,
reuse decisions, and artifact links in `findings.md`; put executed commands,
exit codes, receipt paths, corrections, and remaining blockers in `progress.md`.
Follow PWF's ledger and attestation instructions when applicable. A gated plan
does not waive Archify's validation or establish completion by itself.

Before handoff, record the exact specification and HTML paths, receipt hashes,
automated browser evidence, and actual perceptual review as separate results.
Include `PLAN_ID`, `PLAN_DIR`, and evidence paths with the usual Archify handoff.
Report partial or failed checks truthfully and leave required unfinished plan
phases open. The diagram request alone does not authorize implementation changes
in the project being diagrammed.
